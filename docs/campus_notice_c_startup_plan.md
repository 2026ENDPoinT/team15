## 3 A·B와 맞출 인터페이스

### 3.1 A에게 제공

`Profile`, `NoticeAnalysis`, `AnalysisEnvelope`, `NoticeActions`와 가상 정상 공지를 제공한다. 화면은 `NoticeActions`를 통해 사용자 동작을 호출한다. 상세·카드가 소비할 camelCase 읽기 모델과 변환 경계는 A·B가 함께 정한다. API/저장 봉투는 snake_case 그대로 유지한다.

### 3.2 B에게 요청할 저장 동작

아래는 필요한 동작이며 아직 구현된 함수 이름이나 확정된 시그니처가 아니다. repository의 소유자는 B다.

| 필요한 동작                   | C가 전달할 값                         | B와 확인할 보장                                    |
| ----------------------------- | ------------------------------------- | -------------------------------------------------- |
| 원문 UPSERT                   | CollectedNotice                       | 사용자 진행·체크·마지막 성공 분석 보존             |
| 분석 상태 갱신                | 공지 ID, 요청 해시, 상태, 오류        | 오래된 작업의 성공·실패가 새 작업 상태를 덮지 않음 |
| 성공 분석 반영                | AnalysisEnvelope, 요청 시점 해시·버전 | 현재 본문과 일치할 때만 트랜잭션 안에서 적용       |
| 미분석 저장 후 최초 분석 연결 | 최신 정상 분석                        | 체크리스트를 한 번만 초기화                        |
| 출처별 동기화 결과 저장       | 시도·성공 시각, 실패 건수             | 부분 실패를 전체 성공으로 기록하지 않음            |

분석 반영의 핵심 조건은 `현재 content_hash == 요청 content_hash == 응답 content_hash`다. 공지 ID·schema/extractor 버전도 확인한다. 체크리스트 복사·사용자 상태 보존은 B가 담당하며 C는 체크리스트 SQL을 실행하지 않는다.

본문 변경·분석 성공 후 읽기 모델 갱신과 `reconcileReminders()` 연결도 합의한다. 네트워크·OS 호출은 DB 트랜잭션 밖에서 수행한다.

## 4 이번 코드에서 구체화한 규칙

### 4.1 계약 검증

- `all`과 `specific` 조건에는 빈 문자열이 아닌 근거가 필요하다. `specific` 값은 1개 이상이며 `all`·`unknown`은 빈 배열이다.
- 확정 일정은 실제 날짜와 Asia/Seoul 시간대를 요구한다. 현재 지원하지 않는 시간대는 `needs_review`로 전달한다.
- 날짜 정밀도에서는 시각이 null이고, 시각 정밀도에서는 HH:mm이 필요하다. 미확인 일정은 후보와 근거를 보존하지만 자동 일정 대상이 아니다.
- 모든 객체는 선언되지 않은 키를 거절한다. 요청에 프로필·사용자 체크 기록을 넣지 않는다.
- 본문 20,000자, 링크·첨부 각각 30개를 넘는 AI 요청은 거절한다. 수집 원문에는 이 제한을 적용하지 않아 원문 보존과 원문 확인 안내가 가능하다.
- 외부 링크는 HTTP(S)만 허용한다. 해시·UTC 시각·계약 버전의 형식을 검증한다.

이 스키마는 원문 근거의 의미나 실제 출처를 인증하지 않는다. 원문에 없는 근거·URL·연도 처리, 입력 해시 재검산, 서버 봉투 생성은 T05에서 구현한다. 128 KiB 제한은 Worker가 실제 요청 바이트를 읽을 때 적용한다. 토큰 검증·호출량 제한·시간 제한도 아직 구현하지 않았다.

### 4.2 정규화 c1

1. 입력은 HTML 정제 후 제목·본문·링크·첨부·이미지 여부다.
2. 텍스트는 NFC·LF로 통일하고 줄 안의 수평 공백을 정리한다. 문단 구분을 유지하며 연속 빈 줄만 정리한다.
3. URL은 URL 파서의 직렬화를 사용하되 query·fragment를 제거하거나 재정렬하지 않는다.
4. 링크·첨부는 정규화 결과가 완전히 같은 항목만 중복 제거하고 문자열 순서로 정렬한다. 기기 locale에 의존하지 않는다.
5. 고정 키 순서의 JSON에 정규화 버전 c1을 포함하고 UTF-8 SHA-256을 계산한다.

ID·출처 URL·수집 시각·schema/extractor 버전은 내용 해시에서 제외한다. 분석 캐시 재사용 시에는 별도로 schema/extractor 버전도 비교해야 한다. SHA-256 함수는 주입하며 shared에서 Node나 Expo SDK를 직접 import하지 않는다. Node 테스트에서 고정 해시를 확인했고 Expo·Worker의 같은 값 확인은 각 환경 구현 시 수행한다.

## 5 샘플과 검증 범위

[샘플 사용법](../fixtures/README.md)에 정상·날짜만 있음·연도 미확인·첨부 중심·본문 변경의 입력과 기대 동작을 정리했다. 모든 샘플은 가상 데이터이며 실제 공지로 소개하지 않는다.

```sh
npm ci
npm run check
git diff --check
```

자동 검증은 잘못된 날짜·필드 조합·위험 URL·초과 입력 거절, 샘플 간 ID·해시·근거 일치, 정규화 안정성에 집중한다. 순서만 바뀐 링크는 같은 해시를 만들고 마감·첨부·이미지가 바뀌면 다른 해시를 만든다.

SQLite 보존·오래된 응답 적용 방지·체크리스트 UUID 유지·알림 취소는 후속 통합 테스트 대상이다. 지금 제공하는 변경 샘플만으로 해당 기능이 구현되거나 검증된 것은 아니다.
