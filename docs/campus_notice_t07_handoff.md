## 2 실행 규칙과 설계 조정

1. 기존 가상 시연 진입을 유지하기 위해 첫 수집은 **맞춤 공지 → 실제 공지 새로고침**으로 시작한다. 출처별 시도 기록이 생긴 뒤에는 앱 시작·포그라운드 복귀 시 30분 기준 자동 갱신한다. 설계의 첫 실행 자동 수집과 다른 부분이다.
2. 수동 갱신은 마지막 시도 후 30초, 자동 갱신은 30분 기준이다. 진행 중이면 같은 Promise를 반환한다. 시간은 기기 시각 기준이며 서버의 429 제한이 최종 호출 제한이다.
3. 출처별 최대 2페이지·30건을 수집한다. 출처는 순차, 상세 HTTP 동시 요청은 최대 2건이다. 성공한 원문부터 저장하고 진행 건수를 갱신한다. 실제 공지 카드는 최신 AI 분석 완료 후 표시한다.
4. 목록 밖의 저장한 진행 중 공지도 상세를 다시 수집한다. 목록·상세 실패 시 기존 데이터와 성공 시각을 보존한다. 일부 실패는 전체 성공으로 기록하지 않는다.
5. AI는 전체 큐에서 동시 1건, 자동 갱신당 최대 10건이다. 저장한 공지 → 사용자가 연 상세 → 제목·본문의 관심 키워드 일치 순서로 분석한다. 이후 키워드가 일치하지 않는 공지도 분석한다. 한 번에 최대 10건을 처리하고 나머지는 숨긴 채 대기한다. 목록의 남은 공지 분석 버튼으로 재수집 없이 이어갈 수 있다.
6. 해시·schema·extractor가 같은 정상 분석은 재사용한다. 401·미설정·버전 불일치는 토큰 설정을 다시 적용할 때까지 큐를 중지한다. 429는 `Retry-After`를 SQLite에 저장하고 앱 재실행 후에도 대기한다. 대기 종료 시 자동 타이머 재호출은 없으며 다음 갱신·남은 공지 분석·상세 요청에서 다시 시도한다.
7. 본문이 바뀌면 원문 저장 직후 알림을 재조정하고, 분석 성공 후 다시 재조정한다. 이전 분석은 삭제하지 않지만 최신이 아니면 확정 일정·자동 알림에서 제외한다. 기존 체크 UUID·완료·진행 상태는 유지한다.
8. 앱 시작 시 남아 있는 `running`을 `pending`으로 복구한다. 네트워크·OS 알림 호출은 DB 트랜잭션 밖에서 실행한다.

프로필·키워드 설정은 최신 main의 SQLite 영속화를 통합했다. 지원 자격 판정·추천 순위 고도화는 기존 A/B 범위다. 현재 키워드는 실행 중 동기화 우선순위에도 전달한다. Worker 모델·프롬프트·비밀 설정은 변경하지 않았다.

## 3 B repository 추가 인터페이스

기존 `upsertRawNotice`, `applyAnalysis`, 사용자 동작과 체크 초기화 경계를 사용했다. C 통합에 필요한 메서드는 같은 repository에 추가했다.

- `listNoticeRecords()`: 원문·분류·진행·최신 여부·분석 상태 조회.
- `beginAnalysis({ noticeId, contentHash, requestId })`: 현재 본문에만 작업 시작.
- `applyAnalysis(envelope, request?)`: 요청 ID·해시가 현재 작업과 맞을 때만 반영. 기존 샘플 호출의 인자 하나 형식은 유지.
- `failAnalysis(request, status, error)`: 같은 작업에만 실패 반영. 같은 해시라도 이전 요청의 늦은 실패가 새 요청을 덮지 못한다.
- `recoverInterruptedAnalysis()`: 중단된 작업 복구.
- `beginSourceSync`, `finishSourceSync`, `getSyncState`: 출처별 시도·전체 성공·실패 건수 조회와 저장.
- `setAnalysisRetryAt`: 429 대기 시각 보존.

DB `user_version=2` migration은 `analysis_request_id` 열과 `sync_control` 테이블을 추가한다. 기존 공지·체크·알림 행을 삭제하지 않는다. B가 이후 저장 계층을 변경할 때 이 요청 식별자 조건과 최신 분석 판정을 유지해야 한다.

토큰 원문은 채팅·스크린샷·커밋에 넣지 않는다. 설정 화면의 성공 표시는 저장 성공이며 서버 인증 성공을 뜻하지 않는다. 실제 분석 성공으로 인증을 확인한다.

## 7 분석 완료 카드와 진행 상황 표시 (2026-11-14)

미분석·분석 중·실패·미지원·이전 해시/버전의 실제 공지는 맞춤 공지·메인·휴지통의 제품 카드에서 숨긴다. DB 원문·저장 상태·체크 기록은 보존한다. 수작업 가상 시연 카드는 AI 큐와 진행 건수에서 제외한다. 날짜가 확인 필요인 것은 분석 실패가 아니므로 정상 분석이 끝난 카드는 계속 표시한다.

맞춤 공지에서 완료/전체, 분석 중·대기·실패·분석 불가 건수와 진행 막대를 표시한다. 실패나 일시 중단을 완료로 계산하지 않는다. 토큰이 없으면 AI 분석 설정으로 이동하고, 남은 공지 분석은 기존 수집 결과를 대상으로 최대 10건을 순차 처리한다. 중복 실행·401/409 중지·429 대기 규칙은 유지한다.

Node 24.22.3에서 타입 검사·자동 테스트 117건·Prettier와 Chromium UI 테스트 9건을 통과했다. UI 테스트는 AI 응답을 지연시켜 원문 카드가 나오지 않는 것과 0/2 진행 표시, 완료 후 카드 노출을 확인한다. 변경 후 AI 실패 시 저장 카드를 숨기고 재분석 성공 후 체크·신청 상태와 함께 복원하는 시나리오도 검증한다. 새 Android 실기기 검증은 수행하지 않았다. 후속 e2 운영 배포와 버전 불일치 복구는 [T05 8절](campus_notice_t05_handoff.md#8-e2-운영-배포와-버전-불일치-복구-2026-11-14)에 기록했다.

PR 통합 시 최신 main `bd08609`의 단과대학 필터·프로필 영속화·공지 UI를 함께 반영했다. 요약 중복 제거와 카드별 신청 상태 버튼을 유지하면서 일정 원문/후보 표시를 결합했다. 통합 후 `npm run check` 120건과 웹 UI 10건을 확인했다. UI 테스트는 상태 변경 버튼을 해당 공지 카드 안에서 찾도록 보정했다. 화면 예시는 [분석 진행 상황](screenshots/notice_analysis_progress.png)과 [추정 일정 카드](screenshots/notice_inferred_dates.png)에 보관한다. 캡처 HTML·기록된 AI 응답을 사용하는 브라우저 테스트 화면이며, 진행 화면의 일부 수집 실패는 fixture 범위 밖 공지에 대한 mock 응답이다.
